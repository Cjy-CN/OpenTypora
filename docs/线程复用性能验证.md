# 搜索与文档分析线程复用

本次优化保留搜索和分析算法，只改变线程生命周期与任务调度。基于 0.1.4 工程完成，版本号与发布产物另行管理。

## 跨文件正则搜索

- 每次 `searchFiles` 调用独占一个 `RegexSearchWorker`，按文件顺序复用，不同窗口或并发请求不会共用线程。
- 第一个需要搜索的文件才创建线程；普通文本搜索、空查询、提前取消不会创建线程。
- 保留单文件 1 秒超时、UTF-16 匹配位置、Unicode 整词与零长度匹配、20000 个命中上限、部分失败结果。
- 超时、取消、异常后终止线程；仍需处理其他文件时创建新线程。
- 搜索结束或失败都会等待线程释放。

## 大纲与字数统计

- 超过 20000 字符时，在每个分析 Hook 的生命周期中复用一个 Worker。
- 一个正在执行的任务加一个最新待处理任务，连续修改会替换尚未发送的旧任务，避免累积所有输入快照。
- 所有请求与响应带任务编号；取消只取消结果订阅与未发送任务，正常执行中的线程可继续复用。
- 保留字数统计的 60 ms 防抖与后台任务的 10 秒超时。过期结果不会覆盖当前正文、严格语法或阅读速度对应的结果。
- 线程异常、响应失败、发送失败或超时会终止线程；有最新待处理任务时自动重建并处理，否则等待下一次请求重建。
- 切回短文档或组件卸载时释放线程；重新打开长文档按需创建。
- 常驻线程会保留工作集；本次验证的是复用数量与释放行为，没有将任务耗时下降解释为应用内存下降。

## 正式实现的前后对比

日期：2026-10-06。Windows x64，Intel Core i5-12400F，Electron 44.5.1 / Node.js 24.21.0。

搜索运行于 Electron 内置 Node.js；文档分析运行于隐藏的真实 Chromium 窗口，使用实际 React Hook 和 Worker，用户数据与测试文档均隔离。

| 场景 | 修改前中位数 | 修改后中位数 |
| --- | ---: | ---: |
| 100 个约 6.2 KB 的文件，正则搜索 5000 个命中 | 1763.8 ms | 49.4 ms |
| 34540 字符，大纲分析 | 33.1 ms | 6.1 ms |
| 34540 字符，字数统计 | 24.6 ms | 7.6 ms |
| 198890 字符，大纲分析 | 60.1 ms | 22.5 ms |
| 198890 字符，字数统计 | 45.6 ms | 28.0 ms |

搜索进行 3 轮，交替前后实现的先后顺序，文件系统缓存预热；命中对象逐项比较一致。分析每种文档进行 3 轮，每轮 8 次更新；每次与同一源文档计算的大纲、UTF-16 位置、字数逐项比较一致。

连续 48 次普通更新，大纲和统计总共从创建 96 个线程降为创建 2 个线程。包含严格语法、阅读速度变化、短文档切换、重新打开长文档的整个测试流程，累计创建数从 102 个降为 4 个；组件卸载后全部释放。

搜索数字包含整个 `searchFiles` 服务，尚未包含展示结果。分析数字仅为线程任务耗时，不包含 React 渲染或 60 ms 防抖；两类分析可能并行，节省的时间不能相加当成编辑延迟。结果依赖文档内容与机器负载，不能换算为整个应用的加速倍数。
